Most computation in Geno is always allowed. Anything that touches the world outside the program needs a capability granted on the command line. If you do not grant it, the call fails at the moment it is made, naming the builtin and the capability it needs.

$ geno run notes.geno
Runtime Error: Capability denied: 'fs_read_text' requires the 'fs' capability
Hint: grant it with --cap; the program stays process-isolated:
  geno run --cap clock,fs,print,random notes.geno

The ten capabilities

CapabilityUnlocks
printConsole output
clockTimestamps, timing, sleep_ms
randomRandom numbers
fsReading, writing and listing files
httpOutbound HTTP and HTTPS requests
regexRegular expressions
envEnvironment variables and CLI arguments
processRunning other programs
stdinReading standard input
serveListening for HTTP requests

The mapping from builtin to capability is declared once, in geno/builtin_manifest.py, and every execution surface derives its checks from it. A new effectful builtin cannot ship without saying which capability it needs.

Each surface, honestly

geno run compiles to Python and runs it in a separate, resource-limited process. print, clock and random work; everything else is denied.

geno run --cap fs,print grants exactly the capabilities you list and nothing implicit, in that same process and under the same limits. With env, the program sees its arguments but only the environment variables named with --allow-env. process and serve are refused before the program starts, because what they start would outlive the process's limits.

geno run --unsafe --cap process,print uses the direct interpreter with exactly the capabilities you list, without process isolation. It is for trusted code, and for the capabilities the isolated process does not grant.

geno run --json and the embedding API grant nothing unless asked. They run in your process with cooperative limits, so use the hosted server or your own worker process for untrusted code.

geno serve lets an operator decide which capabilities requests may ask for, and each request receives only the subset it asked for.

Compiled Python reads --cap from its own command line and denies everything without it.

Compiled JavaScript is the exception. --cap controls which APIs are wired up, but generated Node.js code is not a sandbox. Treat it as trusted code, which is how the security policy describes it too.

Granted does not mean unlimited

Granting fs, http or process still applies scoped policies in the isolated geno run process, in the interpreter and in compiled Python: filesystem roots, read-only modes, blocked private network addresses, redirect limits and response-size caps. The isolated process also caps file writes, at 64 MiB per file and per run by default. The capability reference lists them per surface.

Why the command line?

Because that is where a person decides to run something. A model can write fs_read_text("/etc/passwd"). It cannot also grant itself the right to execute it, and the line that would grant it is short enough to read before pressing Enter.

Updated 2026-11-05 for the 0.7 development line: the default geno run lane now accepts --cap and keeps its process isolation (proposal 0013). Before, it refused every --cap, and the hint above sent you to --unsafe.
