# Proposal 0000: 0.5 Stable Promotion

- Status: Draft
- Authors: Codex (AI-assisted draft for maintainer review)
- Created: 2026-10-14
- Discussion: https://github.com/davidiach/geno-lang/issues/177
- Supersedes: None
- Amends: [Proposal 0001](0001-executable-entrypoint-exit-semantics.md),
  Rollout And Observability, prerelease-only publication restriction

## Summary

Permit a non-prerelease `v0.5.0` only after the frozen 0.5 release candidate
meets the acceptance criteria below. This is a proposed, narrow amendment to
proposal 0001's instruction to publish only as a v0.5 prerelease. Its language,
compatibility, security, migration, and evidence requirements remain in force.

The feature baseline is the published `v0.5.0-rc.1`, commit
`e0606a6aea1d8da63b539a7eacc47bf49d4f0654`. This proposal introduces no language,
runtime, API, tooling, or supported-target features. Opening this proposal does
not accept it or authorize stable publication. Stable promotion requires both
recorded human acceptance and the complete release evidence described here.

## Motivation

[RC.1 is published on GitHub][rc-release] and [PyPI][rc-pypi], with green release
checks and installed-package smoke results. The remaining decision is when that
same feature set is eligible for stable publication. Proposal 0001 deliberately
reserved that decision for a later proposal; passing RC checks alone does not
remove its prerelease restriction.

An explicit promotion gate gives evaluators time to exercise the release,
requires actionable reports to be resolved, and prevents release preparation
from becoming another feature cycle. The observation period below is a new
proposed requirement, not a claim that existing policy already mandates it.

## Guide-Level Design

Users can evaluate `geno-lang==0.5.0rc1` now. If this proposal is accepted and
the release gates pass, `geno-lang==0.5.0` becomes the non-prerelease package and
`v0.5.0` the corresponding GitHub release. No additional opt-in flag or new
execution mode is introduced.

"Stable" here identifies a non-prerelease version within Geno's existing
[pre-1.0 compatibility policy](../operations/compatibility-policy.md). Geno
remains a preview project with the component readiness levels in
[MATURITY.md](../MATURITY.md). This does not grant the separate
[serious-beta qualification](../operations/serious-beta-qualification.md),
change package maturity classifiers, or assert organizational production
readiness. The current maintainer and support limitations stay visible.

## Reference Design

### The precise amendment

After acceptance, proposal 0001's Rollout And Observability item 3 is amended
to mean:

> Publish v0.5 prereleases with curated breaking-change notes. Publish v0.5.0
> as a non-prerelease only after the accepted 0.5 Stable Promotion proposal's
> candidate acceptance and final publication gates are satisfied. After that
> qualified 0.5.0 publication, permit non-prerelease 0.5.x maintenance releases
> under the same frozen contract, compatibility policy, and release runbook.

The observation and promotion checklist here governs the first stable 0.5.0.
Subsequent 0.5.x patches use the existing runbook's reviewed, fully gated
rollback/hotfix process without needing a new stable-promotion proposal or this
first-release observation period. This does not authorize features or contract
changes in a patch, or waive any existing patch-release check.

All other provisions of proposal 0001 remain effective. While this record is
Draft, the existing prerelease-only restriction remains effective in full.
Acceptance and permanent numbering follow the [proposal process](README.md);
the implementation PR then updates the rollout cross-reference and release
metadata. This draft does not edit the accepted record.

### Frozen scope

The RC.1 source commit above is the comparison baseline. Every subsequent
candidate and the final stable commit must have a reviewed diff against it.
Allowed changes are limited to:

- Minimal fixes for demonstrated regressions, security defects, or failures of
  the documented RC contract, with a reproducer and affected regression tests.
- Corrections to migration instructions, release notes, and evidence.
- Acceptance/numbering of this proposal and the version, changelog, and package
  metadata changes strictly necessary to publish the approved release.

New syntax, builtins, APIs, CLI switches, templates, targets, expanded
compatibility promises, and unrelated refactors or optimization work are
deferred. In particular, default isolated-run capability selection
[#68](https://github.com/davidiach/geno-lang/issues/68), alternate entrypoints
[#80](https://github.com/davidiach/geno-lang/issues/80), an agent template
[#67](https://github.com/davidiach/geno-lang/issues/67), performance expansion
[#51](https://github.com/davidiach/geno-lang/issues/51), and new external-corpus
CI integration [#81](https://github.com/davidiach/geno-lang/issues/81) are not
added to 0.5.0. Existing external-corpus validation still runs.

No test, security boundary, coverage floor, conformance expectation, performance
budget, or validation baseline may be weakened to obtain a passing release.
If a necessary fix requires a new feature or a contract change, stop promotion
and seek a separately reviewed design; do not widen this freeze implicitly.

### Human acceptance of the proposal

This promotion-only proposal remains publicly open for at least seven days
before acceptance. If its scope becomes a breaking language, security-boundary,
or governance change, the proposal process's fourteen-calendar-day minimum
applies. This proposal changes no decision rights or independent-review rules.

Acceptance requires a recorded decision by the project lead and at least one
independent human technical review under [GOVERNANCE.md](../../GOVERNANCE.md).
Record the reviewer, review URL, material objections and their disposition, and
the lead's decision. Author self-approval and automated/Codex reviews do not
satisfy independent human review. With the current single-maintainer setup,
an external reviewer must be identified; opening or merging this draft alone
is not signoff.

## Backend And Target Parity

The supported-target matrix remains unchanged. Candidate evidence must cover
the existing interpreter, isolated CLI, unsafe CLI, JSON CLI, generated Python,
Node script, directly executed Node ESM, browser, and hosted boundaries as
applicable under proposal 0001. It must establish:

- `main() -> Unit` exits 0; `main() -> Int` returns 2 as status 2, 258 as status
  2, and -1 as status 255 on process-based executable targets.
- Output printed before return is preserved. A normal nonzero integer result
  adds neither an implicit `=> N` line nor a traceback/runtime diagnostic.
- JSON retains the raw result, including exact large integers, with normalized
  process status and empty diagnostics for a normal integer return. A genuine
  runtime error still fails with a diagnostic.
- Embedding returns the raw value and leaves the caller running. Importing
  generated Python or Node ESM is inert. Browser behavior retains its existing
  display semantics without a process status or new Node dependencies.
- Existing async/aliased entrypoint and non-`Unit`/`Int` behavior remains covered
  by the retained tests and conformance cases. Hosted capability denials remain
  fail-closed.

Existing focused tests, all-backend conformance, and installed-distribution
smokes provide this evidence; no new backend or public contract is introduced.

## Compatibility And Migration

Promotion itself introduces no additional source, runtime, diagnostic, API,
package-format, or artifact-format break relative to the accepted candidate.
The 0.4-to-0.5 changes still require the complete migration notes already
published with [RC.1][rc-release] and the [0.5 specification](../spec/v0.5.md).

In particular, an integer returned by `main` now controls process status instead
of being displayed as `=> N`. A caller that wants a displayed result should
print it and return `Unit`. Shell `set -e` and subprocess `check=True` users
must account for intentional nonzero exits, including valid JSON responses.
Embedding continues to receive the raw return value. The release notes must
also retain the RC's stricter type/import validation and async migration notes,
plus the documented capability, entrypoint, and experimental-tooling limits.

The v0.4 conformance corpus stays frozen; the v0.5 specification and corpus
remain the accepted compatibility contract. A regression fix may add a case
that enforces that contract, but may not rewrite old expectations to hide a
behavior change.

## Security And Resource Limits

Promotion does not alter capabilities, process isolation, cooperative timeouts,
memory/step/response limits, host callbacks, or generated-code trust boundaries.
`geno.run()` and JSON mode retain their documented in-process limitations;
generated JavaScript continues to require a trusted execution environment.

Any new open sandbox or capability finding blocks promotion under the release
runbook, regardless of the soak time or other green checks. Dependency audits
and locked installs must pass without suppressing findings to ship. Record a
release owner, a second engineer reviewing the release diff/gate evidence, and
an incident/support owner with the access needed to respond. Roles may overlap
as the runbook permits; independent proposal review must still be independent.

## Testing And Validation

### Candidate acceptance checklist

All criteria below must be evidenced before preparing the final stable tag.
The release evidence must include URLs or retained logs, exact commits and
artifact hashes, environments, commands, outcomes, and reviewer signoff.

- [ ] **Identified candidate:** record the immutable RC tag, source SHA, wheel
  and sdist SHA-256 hashes, publication times, and reviewed delta from RC.1.
  Verify GitHub and PyPI distribute the tested artifact bytes.
- [ ] **Observation period:** the final candidate has been publicly available
  on both GitHub and PyPI for at least seven days (168 hours), measured from
  the later publication time. Record the start and end in UTC. This period and
  the proposal review window may overlap; neither substitutes for the other.
- [ ] **Triage complete:** review all RC feedback and open issues affecting the
  frozen contract at the end of the observation period. No unresolved wrong
  result, backend/exit-contract mismatch, supported-platform install failure,
  crash, data loss, security boundary defect, or required-gate failure remains.
  Document the rationale, owner, and user-visible limitation for any deferred
  report; an enhancement request outside the frozen scope is not by itself a
  blocker. Untriaged reports of these failures block promotion.
- [ ] **Existing automated gates:** the candidate passes the canonical local
  release gate, hosted Python 3.10-3.13 and supported OS matrix, security suite
  and bounty corpus, dependency audits, all retained conformance with Node
  required, and the existing Scheduled Quality performance/deep-fuzz jobs.
  Record the tested source SHA for each run. Keep the 80% coverage minimum,
  existing performance budgets, and expected conditional skips explicit.
- [ ] **Installed-package behavior:** fresh wheel and sdist installs pass
  `scripts/smoke_installed_geno.py`, `scripts/smoke_clean_install.py`, and the
  exit/output/JSON/embedding/import cases
  above, denied-capability and genuine-runtime-error cases, and the runbook's
  post-release checks. Use the published candidate artifacts, not an editable
  source checkout, and record Python and Node versions and platforms.
- [ ] **External dogfood:** against that same published candidate, run all
  101 applications in [geno-corpus][corpus] at
  `977644bbc4a7ca3b0210cf8f024d9c9c67be2b42` through their existing test, run,
  and Python-compile checks. Run the six clean/broken CLI and compiled Python/
  Node cases for [geno-sitecheck][sitecheck] at
  `767c435cd1e2ac864b5e8e92980b317669f524a1`, retaining the minimal migration
  patch and checking exact output, status 0/2, and empty error output. Record
  the driver commands, pinned sources, any patches, environment, artifact hash,
  and logs so another reviewer can reproduce the runs.
- [ ] **Human migration review:** the independent technical reviewer inspects
  the installed-package and dogfood evidence and records whether the migration
  guidance matches the observed behavior, with any objections resolved. This
  is not a claim of a minimum user count or of broad production adoption.
- [ ] **Release handoff:** named release, review, and incident/support owners
  confirm the final checklist, known limitations, support route, and rollback
  plan. The accepted proposal and independent review are linked.

Use the established commands and workflows; this proposal adds no new CI
system. The [release runbook](../operations/release-runbook.md), [Makefile](../../Makefile),
and [local CI guide](../operations/local-ci.md) remain the command references:

```sh
make release-check
make security
make dependency-audit
python3 scripts/run_conformance.py --all-retained --target all --require-node
```

The release wrapper `python3 scripts/local_ci.py release` is also supported.
The existing Scheduled Quality workflow supplies performance and deep-fuzz
evidence. A passing PR check is not a substitute for the complete release gate.

## Rollout And Observability

1. **Review this draft.** Keep status Draft and number 0000 until the public
   review window, independent review, and lead decision are recorded. After
   acceptance, assign the permanent number and merge the design record under
   the existing process. Acceptance does not itself mark the RC gates complete.
2. **Observe and qualify the final RC.** Any code, dependency, build,
   executable-behavior, security, or package-content fix requires a new RC tag
   and version, fresh affected validation and full release gates, and a restart
   of the seven-day observation period. Do not replace RC.1's tag or artifacts.
   Repository-only editorial/evidence corrections that cannot change installed
   bytes or behavior may retain the existing candidate and observation clock;
   the reviewer must record the diff and why that exception applies. A
   correction to migration or contract guidance must receive human review and
   be tested against the installed RC before its checklist item can pass.
3. **Prepare a separate stable implementation PR.** Only after candidate
   acceptance, change the aligned version metadata to `0.5.0`, finalize the
   changelog/migration notes, and link the accepted proposal and evidence.
   Every runtime or packaging fix must already have shipped in the qualified
   RC; the stable diff may contain only reviewed release metadata and docs.
   Verify alignment with `python3 scripts/check_version_alignment.py`. Review
   the complete RC.1-to-final diff, including any intervening main changes;
   do not absorb unrelated work merely because it merged to main.
4. **Validate the exact final commit.** Require green main and
   hosted supported-platform CI, a fresh canonical local release gate and
   security/dependency/quality checks on the final stable SHA. Obtain human
   release signoff for that exact SHA before pushing a tag. The reviewed
   version/docs-only promotion delta in step 3 does not itself require another
   RC observation period; any other change returns to step 2. RC.1 results do
   not replace this final-version validation.
5. **Publish and verify.** After the preceding gates and signoff, push the
   `v0.5.0` tag to trigger the existing publishing workflow. That workflow must
   pass its tag/version/main checks and canonical gate, build wheel and sdist
   once, and pass strict Twine validation and installed-artifact smokes before
   uploading those same tested bytes to PyPI as `0.5.0`. After the workflow
   succeeds, publish the non-prerelease GitHub release with those artifacts,
   curated migration notes, known limitations, source SHA, checksums, and
   evidence links. Verify public GitHub/PyPI hashes and repeat fresh
   public-install and runbook smokes. Publication is not considered complete
   until they pass.
6. **Respond to regressions.** The named incident owner triages reports. A
   failed post-publication smoke stops promotion announcements and triggers
   the runbook's revert/forward-fix process and a newly versioned, fully gated
   patch release as appropriate. Never rewrite public history, move a released
   tag, or replace uploaded artifacts. Keep the RC release and evidence intact.

There is no promised stable publication date. The earliest eligible time is
the later of completion of the proposal review window and the final candidate's
observation period, and all remaining criteria must also be met.

## Alternatives

- **Continue prereleases indefinitely:** preserves proposal 0001 as written,
  but supplies no reviewable decision for stable promotion.
- **Promote immediately because CI is green:** omits public observation,
  migration feedback, and the required independent human decision.
- **Expand 0.5.0 to close all open enhancements:** breaks the freeze and changes
  the candidate being evaluated. Defer those enhancements to later work.
- **Require serious-beta qualification for this version number:** conflates a
  non-prerelease tag with a separate organizational/product readiness claim.
  Keep that qualification, including its staffing and longer evidence gates,
  independent and do not claim it for this release.
