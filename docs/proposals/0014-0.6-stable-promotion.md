## Summary

Permit a non-prerelease `v0.6.0` under the project-lead acceptance recorded below,
after all final technical checks pass. The baseline is published
`v0.6.0-rc.3`, commit `4e70283e04f1521cc1164a270e2b8a9d63ba30e7`.
This proposal introduces no language, runtime, API, dependency, or target feature.

The lead accepted this proposal and explicitly waived its seven-day review
window on 2026-10-24. Publication remains conditional on all technical checks;
the decision does not authorize bypassing a failed check.

## Motivation

The 0.6 changelog reserves stable promotion for a separate proposal. RC.1
introduced the accepted 0.6 language work; RC.2 fixed four confirmed defects;
RC.3 fixed the remaining confirmed Windows package-cleanup, TypeScript Option,
and imported-constructor regressions. Its local and publishing release gates,
supported-platform CI, artifact verification, and fresh public-install checks
passed. These results make RC.3 a concrete candidate, not an automatic stable
release decision.

## Guide-Level Design

Users may evaluate `geno-lang==0.6.0rc3`. After acceptance and qualification,
`geno-lang==0.6.0` is the non-prerelease package and `v0.6.0` its GitHub
release. The versioned [0.6 specification](../spec/v0.6.md) becomes normative
for the 0.6 series; older specifications and frozen corpora remain intact.

The project remains **Preview**, with the existing Alpha package classifier and
component [maturity matrix](../MATURITY.md). A stable pre-1.0 version does not
claim [serious-beta qualification](../operations/serious-beta-qualification.md),
an independent security review, broad adoption, or additional human operators.
The [pre-1.0 compatibility policy](../operations/compatibility-policy.md) applies.

## Backend And Target Parity

Preserve the supported interpreter, isolated CLI, unsafe/JSON CLI, generated
Python, Node script/ESM, browser, and hosted contracts. Retain fail-closed
capability restrictions; generated JavaScript remains for trusted environments.

Validate all retained conformance corpora on every supported backend with Node
required, the Python 3.10-3.13 compatibility matrix, and appropriate Linux,
macOS, and Windows suites. Keep entrypoint exit/output behavior, import safety,
and embedding API results consistent with the frozen contract.

## Compatibility And Migration

Stable promotion adds no break beyond the accepted 0.6 changes already shipped
in RC.3. Retain the 0.5-to-0.6 migration guidance, including Result-only errors,
the coherent standard library, direct imports, and block terminators, and keep
`geno migrate` guidance consistent with installed-package behavior.

Review docs, templates, examples, stdlib and the existing pinned external-app
suite against the final candidate. Fix misleading migration instructions before
publication. Do not count source-only tests as installed-artifact evidence.

## Security And Resource Limits

No capability, sandbox, host trust, or runtime limit changes are proposed.
Any unresolved new sandbox/capability defect blocks promotion. Refresh Python
dependency audits and the extension dependency audit; record existing findings
and their actual exposure without dismissing or suppressing alerts.

The RC.3 evidence records an existing development-only MSAL dependency chain
under VSIX packaging tools. Its production npm audit is clean, and the packaging
gate excludes those tools from the VSIX. Carry that limitation forward only if
fresh triage still supports it; an unchanged advisory is not a claim of a clean
full development audit.

Pre-existing Git objects hardlinked outside a checkout remain protected and may
require manual cleanup. New dependency clones avoid those shared hardlinks.
Document this existing limitation rather than changing external permissions.

## Rollout And Observability

1. Merge this accepted, numbered proposal after its relevant checks pass.
   The explicit lead decision above waives the review interval only.
2. Finalize the separate stable PR: align version metadata to `0.6.0`, add
   curated changelog/migration notes, make the 0.6 specification normative,
   preserve Preview/Alpha maturity, and link this accepted decision.
3. Review the complete delta and run the final gates. Require a clean worktree,
   green integrated main, and matching evidence before tagging.
4. Push annotated `v0.6.0` to invoke the existing publishing workflow. It must
   check version/main ancestry, pass the full gate, build and smoke-test both
   distributions, and publish those exact bytes to PyPI.
5. Verify a fresh public install and public hashes. Publish a non-prerelease
   GitHub release with the tested distributions, curated notes, checksums and
   evidence. Preserve all RC tags/releases and artifacts.
6. For a regression, stop promotion announcements and follow the runbook's
   revert or forward-fix procedure. Never rewrite main or replace released
   artifacts; publish a newly versioned, fully gated fix.

## Alternatives

- Remain on RC.3: valid until acceptance or technical qualification is complete.
- Promote by toggling the GitHub prerelease flag: rejected because package
  version, tested artifacts, specification status and release evidence must agree.
- Bundle new features or broad cleanup: rejected; these require separate
  proposals and candidate qualification.
- Claim serious-beta readiness: rejected; the independent staffing, security
  review and product-evidence requirements remain unmet.
