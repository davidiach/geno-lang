## Motivation

RC.3's hosted latency qualification failed twice. A fixed same-runner comparison
of the earlier and final stable revisions reproduced the same failures with
identical execution inputs; governance documentation was not the cause.
A scheduler comparison passed both configurations on an EPYC 9V74 and did not
establish an affinity repair. No scheduling change was adopted.

The original performance baselines predate mandatory default-backend validation
in check/test. That correct validation now loads the Python compiler, whose
startup parsed the entire trusted runtime prelude to discover module bindings.
Caching that discovery removes unnecessary work while preserving validation.

The project lead directed "Keep held; repair and requalify (Recommended)" on
October 24. That instruction rejected the proposed hosted-performance exception.
Because the repair changes the installed package, proposal 0014 requires a new
versioned RC and an explicit baseline update before stable promotion.

## Guide-Level Design

RC.4 preserves the frozen 0.6 language, API, diagnostics, targets, capability
boundaries, migration guidance and dependencies. Compiler startup performs less
work. Users need no source changes. RC.4 remains a prerelease for evaluation;
only a separately qualified `0.6.0` is the stable package version.

## Reference Design

The compiler hashes the normalized `RUNTIME_PRELUDE` text as UTF-8. Only an exact
SHA-256 match permits reuse of the generated raw 474-name inventory. Any source
mismatch invokes the original AST extractor unchanged, including its errors.
All existing builtin exclusions, reserved-name unions, renaming and rejection
logic remain unchanged.

`scripts/update_prelude_bindings.py` derives the inventory from the uncached
extractor. Ordinary CI verifies the exact source digest, complete name equality,
and deterministic generated contents. This is internal compiler metadata; it
does not change a public generated-program or package format.

After publication, record the actual RC.4 merge/tag commit, tree, workflow,
wheel/sdist hashes and installed-product evidence before considering this new
baseline qualified. A squash may change the commit SHA only if the source tree
matches the fully qualified candidate.

Any further runtime, dependency, build or package-content fix again requires a
new RC and fresh affected validation. Stable may add only the governance,
version and documentation delta already permitted by proposal 0014.

## Backend And Target Parity

Keep interpreter, isolated CLI, generated Python/JavaScript, Node, browser and
hosted behavior unchanged. Backend validation must still run for check/test.
Run supported Python 3.10-3.13 and platform CI, frozen conformance with Node,
deep differential fuzzing, compiler/host-name and capability/security checks.

## Compatibility And Migration

No new source, API or dependency migration is introduced. Retain the existing
0.5-to-0.6 guidance and frozen corpora. The generated Python metadata module must
be included in the wheel and sdist and validated from fresh installed artifacts,
without importing the repository checkout.

## Security And Resource Limits

The cached set is not an alternate security policy. A stale source cannot reuse
it, malformed changed source retains the original failure, and tests compare the
inventory against the uncached parser rather than trusting the digest alone.
Capability gates, sandbox limits, reserved names and all resource policies stay
unchanged. Carry forward only freshly verified residual dependency findings.
